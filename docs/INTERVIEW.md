# 面试讲解

## 项目怎么升级的？

原版是 Java 17 / Spring Boot / MyBatis / MySQL / Thymeleaf 单体。2026-10-24 保留 Service/Mapper 和四角色业务，将页面改为 Vue 3 + Element Plus，JSON Controller 提供接口；新增 Redis 菜单缓存、共享 Session、数据库购物车与跨实例幂等结算。一个 JAR 仍可同源交付，不拆微服务。

## 为什么共享 Session 不能代替结算幂等？

Redis 只能让多个实例读到同一登录身份。两个实例仍可能同时读写业务状态；对本机 cart 加 synchronized 不能锁住另一个 JVM。现在所有购物车修改/结算先在同一 MySQL 事务锁用户行，再校验 version/key。订单以学生 + requestKey 唯一；同 key 同参数返回旧订单，参数不同返回 409。请求指纹只包含实际输入，购物车清空后仍能核对重放。

## 三类数据库保护各负责什么？

用户行锁负责同一学生购物车和下单的串行化；唯一键是幂等订单的数据库防线；条件抢单 UPDATE 负责多个骑手只能一个成功。主表/明细/事件/cart 清空由事务原子提交；事件失败不能留下没有日志的状态更新。

## Redis 缓存为什么允许旧展示，成交价却不允许？

缓存只承载公共店铺/上架菜单的默认页，TTL 为 60–75 秒。改价等操作提交后失效，但并发回填仍可能短暂写回旧展示，不能称强一致。结算重新查 MySQL 有效状态和 BigDecimal 现价，再写快照；不会按 Redis 旧价成交。

## 去掉完整 Spring Security 后安全如何保留？

BCrypt encode/matches 保留旧哈希。Spring Session Redis 管理 Cookie 会话；登录换会话编号和 CSRF。每次请求按 Session 用户编号重新查 MySQL 启用状态/角色，版本变化使旧会话失效。过滤器约束角色，Service/SQL 约束订单/店铺/地址归属。写请求都验证 CSRF，不接受用户头自报角色。Redis Session 故障时 503，不能回本机 Session 或跳过认证。

## 为什么不需要 MQ、分布式锁和微服务？

当前四角色共享订单数据与事务，拆分会增加跨服务一致性成本。超时任务用数据库索引分批扫描、条件更新和启动补偿满足范围；抢单由 SQL 决定，Redis 锁不会增加业务正确性。没有异步削峰场景和真实压测支撑，不能为了技术名词新增 MQ。

## 分页和性能如何证明？

筛选在 SQL WHERE 中，主表 LIMIT/OFFSET 后一次 IN 批量加载本页明细。真实 Redis 集成测试核对默认菜单连续两次读取只触发一次菜单 SQL；关闭缓存则触发两次。这里只陈述查询次数，不把本机测试转成线上 QPS 或延迟承诺。详见验证报告。

## 如何保留旧数据？

V2 只加字段、索引和购物车表。旧订单 requestKey 保持 NULL，不伪造历史幂等键；旧 BCrypt 和 ID、快照、金额、事件保留。已有 JVM Session 购物车需重新选餐。切换和回退前都备份，回退不能直接覆盖为旧快照而丢掉新订单与 cart。
